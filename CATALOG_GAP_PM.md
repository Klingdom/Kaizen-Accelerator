## 2. Gap Analysis Per Bucket

### 2a. PROJECT Bucket

**What exists:** The catalog has strong DMAIC and Kaizen project execution coverage. Every analytical tool (SIPOC, C&E, FMEA, MSA, Control Chart, Capability, Regression) is present. Charter, DCP, baseline, financial benefit, implemented improvements, results narrative, and process owner transition are all defined.

**What is missing:**

1. **Project initiation for non-DMAIC/non-Kaizen work.** The DMAIC Charter (#20) is DMAIC-specific. There is no generic project charter or work-breakdown-structure standard work for everyday project work (product builds, programs, operational initiatives). The `gen_deep_work_project` generic is a time-block placeholder — it provides no initiation discipline.

2. **Milestone and dependency tracking.** No standard work exists for weekly project status updates against a milestone plan. Program Plan Refinement (#19) is in the COMMUNICATION bucket and covers plan updates, but there is no structured status reporting artifact — no blocker log, no RAG (Red/Amber/Green) status discipline, no escalation trigger.

3. **Technical or knowledge-work output specification.** Writing a technical spec, design brief, or product requirements doc is a common deep-work output type. The catalog has Document Writing (#18, COMMUNICATION) and Deep Work generic (PROJECT) but no structured procedure for spec authoring as a distinct project deliverable.

4. **Project closure for non-DMAIC projects.** Lessons Learned (`gen_lessons_learned`) fires on Kaizen close only per its trigger definition ("Every Kaizen close"). There is no equivalent for general project closure: no handoff checklist, no archive step, no "project complete" gate for DMAIC-adjacent or ad-hoc project types.

5. **DMAIC Control Plan.** The catalog has the Control Chart (#29) and Process Owner Transition (#50 for Kaizen). But there is no explicit **DMAIC Control Plan** entry — the document that specifies ongoing monitoring, response rules, and SOP updates for the improved process. The results narrative (#41) mentions a control plan in its procedure but it is not a discrete schedulable artifact.

### 2b. COMMUNICATION Bucket

**What exists:** Six schedulable entries cover time-blocking (14), team meetings (15), 1:1s (16), document writing (18), program plan refinement (19), daily standup (ceremony), mid-sprint review (ceremony), and the generic communication block. This is the thinnest bucket in the catalog — 8 entries vs 32 in PROJECT and 20 in CI.

**What is missing:**

1. **Structured 1:1 format.** Entry #16 ("Connecting w/ teammates") is a 20-min time block with no procedure. A well-structured manager/direct-report 1:1 is fundamentally different from a peer connection and requires its own standard work: standing agenda, forward-looking focus, action tracking.

2. **Stakeholder status broadcast.** There is no standard work for the weekly or bi-weekly written status update sent to stakeholders (project sponsor, leadership, cross-functional partners). This is distinct from internal standup — it is async, outbound, and audience-formatted.

3. **Decision meeting / sign-off.** RACI-driven decisions, escalation meetings, and approval gates are absent from the catalog entirely. These are among the highest-value meetings in any organization; they have a distinct structure (pre-read, decision framing, explicit outcome recording).

4. **Customer or external sync.** No standard work covers an external-facing sync: customer check-in, vendor review, partner update. External comms have a distinct discipline (pre-call prep, follow-up notes, commitment log).

5. **Crisis comms / incident response communication.** Not addressed in any bucket. For teams doing operational or technical work, an incident requires a specific comms cadence (initial notification, status updates, post-incident communication). Even a lightweight entry covering the comms discipline of an incident improves response quality.

6. **Async written update (no meeting).** The existing Document Writing (#18) covers project documentation broadly. There is no entry for the discipline of writing a short async status or decision communication — a "weekly written update to stakeholders" standard that keeps the practice from defaulting to an ad-hoc email.

### 2c. CI Bucket

**What exists:** The CI bucket is the most populated. It has L&D (personal and team), compliance, document review, team intros, the full Innovation pipeline (#6–#11), PDCA, 6S email, four ceremonies, the daily EoAR, weekly reflection, and lessons learned. The daily, weekly, and Kaizen-close cadences are covered. Sprint cadence is covered by ceremonies.

**What is missing:**

1. **Monthly CI review.** There is daily (EoAR), weekly (weekly reflection), quarterly (quarterly planning), and event-driven (lessons learned) cadences. The monthly cadence is entirely absent. A monthly review — looking across 2–3 sprints for trends, reviewing Kaizen portfolio health, checking OKR trajectory — is a standard lean cadence that bridges weekly micro-cycles and quarterly planning.

2. **Annual reflection / career planning.** No annual standard work exists. Annual review of skill gaps, career goals, L&D plan for the year, and review of the improvement portfolio is a standard practice in development-oriented cultures. The L&D tracker (#1/#2) covers continuous learning but not the annual goal-setting and progress review cycle.

3. **5 Whys root-cause analysis.** The catalog has FMEA (#37, #47) and C&E Matrix (#34, #46) for structured root-cause work. But 5 Whys is the most commonly used lightweight RCA tool — done in 15–30 minutes for daily friction signals, operational issues, or short-cycle Kaizens. It is entirely absent.

4. **Standard Work creation and update.** The catalog contains no entry covering how to create or revise a standard work procedure itself — the "meta" CI activity. When a Kaizen closes, there should be a procedure for updating or creating the affected SOP/standard work entry. The lessons learned entry captures the narrative; there is no standard for the SOP update step.

5. **Improvement experiment log / PDCA documentation.** The PDCA Cycle (#12) is a time-block entry (EVERY_48H). Its procedure captures the rhythm but produces a "current-condition measurement" artifact. There is no standard work for formally documenting an improvement experiment — hypothesis, test conditions, results, decision (keep/pivot/abandon). This is distinct from PDCA cadence; it is the artifact discipline around experiments.

6. **Conference / course debrief.** The L&D entries (#1, #2) cover the learning selection and completion cycle. Neither covers the specific debrief practice after completing a course, attending a conference, or reading a book — the step where raw learning is synthesized into actionable insights and knowledge wiki content.

## 5. Open Questions for Phil (SW-Q items)

**SW-Q1 — Project Charter scope.** Should `gen_project_charter` apply to all project types including Kaizen Event (which already has #42) and DMAIC (which already has #20)? Recommend: `projectTypeBinding: null` (general, non-binding), with a note that it is superseded by #20 and #42 when those types are in play. Phil needs to confirm whether general projects are a first-class project type in the OS or always resolved to DMAIC or Kaizen.

**SW-Q2 — DMAIC Control Plan vs Kaizen equivalent.** The Kaizen Process Owner Transition (#50) partially covers control for Kaizen events. Is a separate Kaizen Control Plan needed, or does #50 + the Control Chart (#29 pattern) cover it? This analysis treats Kaizen as covered by #50 and only adds the DMAIC variant. Phil should confirm.

**SW-Q3 — Monthly CI Review participants.** The current recommendation includes "CI Champion" as a participant. If many users of the OS are individual practitioners without a CI Champion, should this be self-only with an optional escalation to Champion? Phil's call based on target user profile.

**SW-Q4 — Annual Reflection timing.** The recommendation anchors to "Q4 final sprint OR first week of new year." This conflicts if the quarterly calendar does not align to calendar year. Phil may want to anchor to "Sprint 7 of Quarter 4 (reset sprint)" instead, which is already in the OS vocabulary.

**SW-Q5 — 1:1 entry vs #16 update.** Option A: Add `gen_structured_1on1` as a separate entry with full procedure, leaving #16 ("Connecting w/ teammates") as the informal peer connection. Option B: Replace #16's empty procedure with the structured content and rename. Option A is recommended to avoid breaking the numbered-entry convention and because the use cases are different (peer vs manager/report). Phil must decide before implementation.

**SW-Q6 — Standard Work Update trigger.** The recommended trigger fires on Kaizen close OR lessons-learned-identified gap. Should it also fire after Sprint Retrospective action items that change a procedure? If yes, the dependsOn should add `cer_sprint_retrospective`. Phil should confirm the full trigger set.

**SW-Q7 — Bucket for Weekly Project Status.** This analysis places `gen_weekly_project_status` in PROJECT (it is a project-management output). An argument exists for COMMUNICATION (it is written communication). The status broadcast (`gen_stakeholder_status_broadcast`) is in COMMUNICATION. Having the authoring step in PROJECT and the distribution step in COMMUNICATION is the recommended split — but Phil needs to confirm this mirrors how time is attributed in the OS budget model.
